## 章节要点

### 第 1 章 Code Review 在流程中的位置（V3 00:00-02:23）

- 公司规则：工期超过三天的开发任务都要 code review [00:00]
- 潜规则的代价：赶进度让「能跑就行」，上线后代码质量差、运行性能差；程序员离职后接手的人看不懂；本想改一个小 bug 却多出三个 bug [00:30]
- 定义：对别人写的代码做审核，确保开发质量，是项目质量管控的重要环节 [00:45]
- 位置：开发结束、准备提测之前 [00:50]
- 顺序：需求 → 设计（设计也要评审）→ 写代码 → code review → 提测 [01:00]
- 提测阶段不应该大量改代码，只该完善：改 QA 提的 bug、兼容极端与边界问题 [01:15]
- 参与角色：代码开发者、技术能力强的人（开发组长、架构师）、QA [01:40]
- QA 为什么要在场：很多 QA 也写代码；听你讲的时候会想「这样做是否符合产品需求」「我设计的测试 case 有没有漏」「这个判断条件是不是全的」「哪些场景会跳过这些判断」[02:00]
- code review 顺便确定本次改动的范围，QA 只测相关业务逻辑 [02:20]

### 第 2 章 审查清单与沟通心态（V3 02:26-06:21）

- 维度一 产品需求：业务逻辑有没有完全实现，有没有漏写的代码 [02:30]
- 维度二 可读性：逻辑是否清晰、有没有注释、是不是重复造轮子（别人已经实现过，只是你不知道）[03:00]
- 维度三 代码规范：入参有没有校验、判空、空集合、查询数据库有没有 limit、权限与数据安全有没有 check [03:20]
- 维度四 对现有逻辑的影响：新功能依赖三方接口，三方挂了会不会拖垮自己主流程（用户下不了单、无法支付）；有没有 try-catch、有没有降级策略；这一步最花时间也最重要 [03:40]
- 维度五 文档：库表改动、接口路径变更要有清晰文档，上线前的发布准备依赖它 [04:10]
- 心态：第一次做 code review，感觉像一件件脱衣服给别人看 [04:20]
- 麻烦：高阶同事没参加过需求评审，不知道你这期要做什么，所以要讲背景；心里清楚的事一遍遍解释容易失去耐心，情绪管理会失控 [04:40]
- 换个姿势：毫无保留地讲清为什么这么做、当初怎么想的，对方理解之后给的建议往往值得采纳，甚至更好 [05:00]
- 「你看不上我、我看不上你」的 review 没有意义 [05:50]
- 有时也要坚持自己的观点：没有绝对好坏，表达观点要有耐心，说服别人本身是重要技能 [06:05]

### 第 3 章 案例：读一个模板解析库的代码（V2 00:00-04:50）

- 项目名吐槽：叫 temparse，读起来像 temp ars，「临时的屁股」冲击力太大 [00:00]
- 从 README 开始：项目核心是从一个字符串里按模板提取数据；模板里大括号的内容决定怎么从原始字符串变成目标数据 [00:20]
- 类型语义：str 保持原样，int 把字符串变成整数；泛型提示返回值类型，对 type checker 友好 [01:00]
- 代码结构：只有一个文件，全部放在 `__init__` 里；小项目这么做也不是不行，但更推荐分文件；市面上确实有项目这么干 [01:40]
- 核心类 `Parser`：用 type variable 表示输出类型，经典 generic 写法，拆包时 type checker 能检查类型对不对 [01:50]
- 借力 t-string：Python 3.14 引入的 t-string 会先把自己的部分 parse 成 raw string 和 interpolations，一部分 parser 的活交给 t-string 干 [02:20]
- 正则：整个字符串用 regular expression 做 match，提前 compile 完还把 property cache 住；值得学——同一个正则要 match 很多次时不要每次重新 match，先 compile 再 match [02:40]
- parse 部分：把每个 match 到的字符串和对应的 interpolation 成对传给 convert [03:15]
- convert 的两个参数：已匹配上的字符串、原来的模板；命名建议不要用 i，i 常被当 index 或 integer 用，改用 s 更好读 [03:30]
- `i.value` 是大括号里的东西求值之后的值：这里是 str class、int class [04:00]
- 用 match case 分派：origin 是 int 就转成 integer，float、complex 同理；整个代码不到 170 行 [04:20]

### 第 4 章 设计层的分歧：装饰器、interface 与一致性（V2 04:53-13:39）

- 引子：AI 加持下很难像以前的 review 那样找细节小问题，AI 加 linter 加 formatter 把蠢问题都消掉了；但 CR 依然有意义，问题从项目角度看 [04:53]
- `parse` 为什么是小写 class：作者故意的，想让用户概念里它是 function；因为当时的 Python 版本没法给函数直接加泛型，这个提案是 Guido 本人提的、还没被接受；为了保住 typing 做的一个 hack [05:40]
- 不一致：`Conversion` 到了装饰器那块却又变成大写开头的 class [06:30]
- decorator 怎么工作：只定义了 `__init__` 和 `__call__`，把圈出来的部分改写一下就明白了 [06:45]
- `FormatConversion`：专门对付带 format 的情况 [07:19]
- 例子：`percent` 把百分号字符串转成 float；除了 `==` 用得不好（浮点世界尽量不写等号）[07:20]
- 追问：这个 decorator 带来了什么？转换完全由大括号里的东西决定，大括号里是 percent 就全局找 percent 函数，把 30% 喂进去 [07:45]
- 作者给 Conversion 找的两个作用：显式规定「percent 是一种转换方式」；规定函数的 argument 数量 [08:06]
- 反驳一：不需要显式规定是 conversion，用户给什么函数就用什么函数转换 [08:30]
- 反驳二：type check 角度没有额外信息，原函数本来就带类型；argument 数量、有没有 format 运行时都能知道 [08:54]
- 结论：conversion 与 format conversion 在设计上压根不该存在，用户直接写一个 conversion 函数传进去即可 [09:20]
- 另一个设计问题：最基础的例子里 string 出现两次、int 也出现两次——要把数转成整数这么常见的事竟然要写两次 int [09:42]
- 泛型那部分可能是必须的（给 type checker 用），但大括号里也必须写吗？既然已经在模板上写了要返回什么值，能不能有默认方式 [09:42]
- interface 设计原则：没有歧义的情况下让用户输入的东西越少越好；同样的数据不要让用户输两次 [10:00]
- 直觉冲突：f-string、t-string 里大括号内容一般表示「要转换什么变量」，作者的设计里大括号里的 percent 表示的是「转换这个 30% 的方式」，方向反了；不熟悉这个库的人第一反应一定是「30% 对应 percent」[10:30]
- 作者的替代方案：t-string 本身提供了 format spec，冒号后面会自动 pass 出来，冒号后面代表格式转换，可以定义「这样就代表我用这个函数转换」[11:00]
- consistency 问题：interface 给用户之后一致性要好，用户顺着你的逻辑应该能明白 [11:30]
- 反例点名 JSON：把 json 扔到大括号里、用 json.loads 把字符串变 dict 或 list；但 json 是 module，没法把字符串 feed 给 module，等于自己开辟了一个新语义 [12:06]
- 修法：用 json.loads 就够了，不用专门给它规定语义 [12:54]
- 还有 list、dict 与 json 语义一模一样，怪；如果支持 list 和 dict，应该做一些 run time 的 type check [13:00]
- 顺带：既然这么在意 type，parse 也应该做 type check [13:40]

### 第 5 章 工程化收尾：覆盖率、CI，以及 AI 之后剩下的问题（V2 13:42-15:15）

- 正式项目还需要什么：测试是有的，但没有 coverage，不知道测试写得够不够 [13:42]
- GitHub workflow 只有一个 publish（上传 wheel），没有测试、没有 lint、没有 format；程序出错压根不知道；想做成正经项目，CI 要做起来 [14:00]
- AI 之后小结：编程小细节上的问题越来越少了，缩进、变量名格式这类琐碎问题基本消失，代码看起来都挺靠谱 [14:30]
- 但从项目角度看，依然有大量可以 review 的问题：design、interface、CI [14:45]
- 这些东西 AI 能做吗。或许能做，但它肯定不是自动做的：不会说「写个这个项目」就把我说的那些全都做了 [14:55]
- 你脑子里得有这根弦：需要不断跟它沟通、不断跟它较劲，它在这方面可能有有价值的见解 [15:05]
- 有没有这个意识去跟它沟通，是作为程序员值得培养的能力 [15:15]

### 第 6 章 判断力：把工作和知识解耦（V1 00:00-09:50）

- 提问：实习做 KV 量化，只能用 agent 替代工作否则会落后，公司也鼓励用，其他实习生都在用；用起来几乎没收获，写好 prompt 让 agent 自己优化算子或框架 [00:00]
- 算子刚开始的优化还能看懂，迭代几轮性能提升后代码晦涩难懂，只能让 AI 解释它优化了什么；目标是看懂优化过程，但自己写不出这么高效的算子，每天只能从大层面了解知识 [00:20]
- 这个问题正常吗。正常，而且不只是实习生，中学大学、科研、已工作的朋友都会有这种感受：AI 在逐渐替代脑力劳动 [01:35]
- 两拨人：已工作的倾向全员做 agent，只做产出验收和极端情况检查；在学习的倾向弄懂每一行代码，把它学清楚，这是核心竞争力 [02:00]
- 两个想法都对，问题的本质在于你要用 AI 来干什么；他既在实习，公司要的是收益和产出，既要产出又要学到东西是比较困难的 [02:23]
- 人在失败中提升：高中数学周考月考期末考，是为了检查出能力边界；圆锥曲线不会做不会怪立体几何做错，因为知道那是知识面不够，下次提升重点就明确了 [03:13]
- 现在的问题：问 AI 时它没有告诉你这个知识属于哪个范围，范围是人裁定的；一个问题可能同时涉及数据库、环境配置、数据结构、AI 知识，作为学习者就 loss 掉了，完全不知道该学什么 [04:01]
- 第一步是确定问题的边界，别把问题摊大到吸收不了的程度 [04:30]
- 建议：把工作和知识解耦——工作中核心目的是达到公司要求、没有严重性能 bug [04:53]
- 学习要明确核心目标和优化方案，以 50~100 行为单位不断迭代自己的知识；假设现在写不出更高效的算子，就在已有基础上做 50 行的重构迭代 [05:00]
- 分工：概念性问题交给 AI（它冒出来一堆没听过的名词时，搜索让它帮你解决），判断性工作留给自己；自己负责判断，AI 负责 if-else 这类逻辑 [05:41]
- 历史类比：工业革命时的卢德运动，一批纺织工人反抗纺织机；上世纪的新卢德运动里会计等岗位被计算机替代；现在这次替代的是脑力 [06:29]
- AI 的边界是判断能力，分三种人 [07:17]
  - 第一种：能力强，只是不想写代码或觉得工作量太大 [07:30]
  - 第二种：能力不那么强，不知道怎么做，希望 AI 帮忙做；基础较好但面对未知知识时不知道哪些要学、哪些要舍弃 [08:05]
  - 第三种：连自己要做什么都不知道，AI 说什么做什么；主要该提升概念性知识和判断力，判断力的前提是大量阅读 [08:30]
- 结论：不可能抛弃 AI，也不能全让 AI 替我们思考；我去做核心的判断和选择，让 AI 补充相关背景知识 [08:57]
